# Clarifications: Agent Workflow Performance and Review Convergence

### Session 2026-07-26

1. **Which tests must remain real Git integration tests?** Unsafe-command rejection before spawn; exact Git target/`dirtyHash` computation (`computeValidationTarget`, `targetsMatch`); fix-cycle and final-validation tree-diff detection (any test whose assertion depends on `getDiffSignature`/`getAnswerStageEditSignature` actually changing after a real filesystem mutation); at least one real SIGTERM→SIGKILL timeout-cleanup test; interruption cleanup; state persistence/resume; BOM-tolerant state loading; dry-run no-write guarantees; real command exit-status handling; human-gate enforcement (`markHumanGate` reachability). These map to the existing tests: "rejects unsafe runner configs before spawn", "rejects unsafe validation commands...", "accepts fix cycles that change content without changing diff stats", "full validation modifying the tracked tree is treated the same as a full-validation failure...", the Reviewer/Implementer timeout tests, the interruption tests, "loads BOM state and persists orchestration state", the `orchestrate dry-run` describe block, and "runs npm validation commands through the real adapter on Windows-compatible argv".
2. **Which tests may safely use fake Git and process adapters?** Anything asserting purely on orchestration decision logic that does not depend on real diff/status content: role selection/swap, question-loop progression, structured-review parsing outcomes, finding-lifecycle classification, run-summary shape/content, budget arithmetic, and the new Part B/C/D modules' own unit tests. The agent process side was already fake in 100% of these tests via the test-local `createSequenceAdapter`; this feature promotes that pattern into `testDependencies.js` and additionally fakes the Git side for this same test subset.
3. **How are shared fixtures isolated?** Each test that still needs a real repository gets its own fresh temporary directory (`fs.mkdtempSync`), populated by an `fs.cpSync` recursive copy of one lazily-created, never-mutated base fixture directory (created once per test-process run, cached in a module-level variable) rather than by re-running `git init`/config/commit. Copying the base fixture, rather than reusing it directly, guarantees per-test isolation identical to today's per-test `git init` — no test can observe another test's mutations.
4. **Can tests run concurrently with the selected fixture strategy?** Yes for the base-fixture-copy tests: `fs.cpSync` targets a fresh `mkdtemp` directory per test, so concurrent tests never share a working tree. The base fixture itself is created once, read-only after creation, and never mutated by any test, so concurrent reads of it for copying are safe. Vitest's existing single-file-sequential execution is unchanged by this feature; this feature does not introduce `test.concurrent`.
5. **What are the baseline and target durations?** Corrected baseline (this session, `main` @ `75c3297`, after excluding a stray worktree that was inflating/concurrently-diluting the first measurement attempt — see `spec.md`'s Baseline section): `orchestrateCommand.test.ts` 417.73s/81 tests/1 file; `npm test` 406.47s/654 tests/42 files. Target per the feature request: under 120s standalone, under 180s full suite. See `spec.md` SC-001 and the final report for the achieved numbers and, if short, the specific remaining bottleneck.
6. **What happens if performance targets are not reached?** Report the achieved duration, the specific remaining bottleneck (e.g., the retained real-Git integration subset's own per-test `collectGitContext` cost), and why further optimization was deferred (e.g., changing `collectGitContext`'s internal batching of `git` plumbing calls is a wider-blast-radius production change affecting every consumer, including the Reviewer-facing prompt content, and was judged out of scope for a "safe" performance change in this feature). This is explicitly permitted by the feature request; targets are not silently claimed as met.
7. **What constitutes a complete review?** A review whose process execution did not time out, error, or get interrupted, **and** whose structured output (when present) does not contain an *explicit* negative signal: `reviewCoverage.stoppedEarly === true`, `reviewCoverage.checklistCompleted === false`, or reported `changedFilesInspected`/`highRiskFilesInspected` that fall short of the deterministic inventory totals. A first implementation attempt made *absence* of `reviewCoverage` itself (or absence of any structured review at all — a plain legacy Markdown decision) count as `incomplete`; running the full existing `orchestrateCommand.test.ts` suite against it immediately broke 44 of 81 tests, because every pre-Spec-056 review fixture (and, in practice, every real Reviewer invocation until it adopts the new prompt) has no way to report the new field. That is exactly the kind of "claims improvement while breaking existing coverage" failure this feature's own validation strategy exists to catch. The corrected rule — implemented in `reviewCoverage.js#computeReviewCompleteness` — treats absence of the new evidence as `complete` (matching every other additive Spec 053-055 field), and reserves `incomplete` for a reviewer that engaged with the new schema and reported an explicit problem.
8. **Must every changed file be explicitly reported as inspected?** Every high-risk file, yes, individually reachable in the deterministic inventory — but only enforced (see Q7) when the Reviewer's output includes a `reviewCoverage` object with numeric fields at all; a legacy or `reviewCoverage`-omitting review is not retroactively judged against this. When `reviewCoverage` is present, low-risk files may be acknowledged via grouped review (a count/pattern statement) rather than one-by-one, per the feature request. The workflow can only verify the *counts* the Reviewer reports against its own deterministic file list — it cannot verify that semantic inspection actually happened; this limitation is documented here rather than silently assumed away, per the request's own admission ("it cannot falsely prove semantic inspection").
9. **How are high-risk files classified?** Deterministically, in `reviewCoverage.js`, based on path patterns already meaningful to this codebase: any file under `tools/agent-workflow/` matching `orchestrateCommand.js`, `reviewCommand.js`, `runSummary.js`, `agentRunner.js`, `structuredReview.js`, `findingLifecycle.js`, `roleResolver.js`, `validationPolicy.js`, `validationPlan.js`, `validationPhase.js`, `reviewCoverage.js`, `reviewConvergence.js`, `reviewBudget.js`, or `performanceMetrics.js` (state machine, safety, or convergence logic); any file with a net line-change (`additions + deletions`) at or above a configurable threshold (default 40); any file touching `.agent-workflow/` path assertions or CLI argument parsing. Everything else is low-risk. This is intentionally a static, auditable rule set, not a learned or fuzzy heuristic.
10. **What happens when a Reviewer stops after the first finding?** Its completeness is computed independent of its decision text: if it reports fewer inspected high-risk files than the deterministic total, or explicitly states it stopped, `completeness = "incomplete"`. An incomplete review is never `Approved`; any findings it did report are preserved (not discarded) and available for the next attempt, and it consumes one `maxIncompleteReviewRetries` slot, not a full `maxReviewAttempts` slot on its own re-run, per FR-010/FR-015 and Smoke B.
11. **How are related-pattern searches represented?** As a required instruction in the review prompt (FR-006/FR-008: "search for the same pattern in nearby branches / similar state transitions / similar parser branches / similar command-selection paths / similar resume code / similar summary code" whenever a blocking finding is identified), not as a separate machine-checkable field — this is a prompting/process requirement, verified by outcome (fewer late-discovered related findings across rounds), not by a schema field the workflow can independently confirm.
12. **How are finding IDs generated and persisted?** Reused unchanged from Spec 052's existing finding-lifecycle machinery (`findingLifecycle.js`): the Reviewer supplies a stable `id` per finding (e.g., `P1-001`); the ledger keys on that ID plus `filePath`/`location` fallback matching already implemented there. This feature's `reviewConvergence.js` sits on top of that existing lifecycle map to add new/known/reopened *classification* and telemetry; it does not reimplement ID assignment.
13. **What is considered a new finding after round one?** A finding whose ID (or fallback identity) does not appear in the ledger from any prior review attempt for the current run.
14. **What is considered a reopened finding?** A finding whose ledger entry was previously `resolved` (or `accepted-non-blocking`) and is reported again with the same identity in a later review attempt; its `reopenedCount` increments and its status returns to `open`.
15. **What are the default review budgets?** `{ maxReviewAttempts: 3, maxAutomaticFixCycles: 2, maxIncompleteReviewRetries: 1, maxReviewerQuestionCycles: 1 }`, matching the feature request's suggested defaults and the existing `DEFAULT_MAX_QUESTION_CYCLES`/`DEFAULT_MAX_FIX_CYCLES` values already in `orchestrateCommand.js`.
16. **How does `--max-fix-cycles` interact with review attempts?** `--max-fix-cycles` continues to mean "maximum automatic Implementer fix cycles" (Reviewer-requested `fixCycleCount`, and separately `fullValidationFixCycleCount` from Spec 055) exactly as before. `reviewBudget.maxAutomaticFixCycles` is resolved as an independent state-level ceiling that, by default, mirrors `--max-fix-cycles` for the Reviewer-requested path so the two never silently diverge unless a state file explicitly overrides `reviewBudget.maxAutomaticFixCycles`; `reviewBudget.maxReviewAttempts` has no pre-Spec-056 equivalent and is purely additive. Precedence when both are supplied: an explicit `reviewBudget.*` value in state or a dedicated `--review-*` CLI flag always wins over the mirrored default from `--max-fix-cycles`.
17. **Can a human resume with a larger budget?** Yes — increasing `reviewBudget.maxReviewAttempts`/`maxAutomaticFixCycles`/etc. in the state file (or via CLI flag on the next invocation) and resuming continues the run from its persisted ledger, attempt counts, and ratchets the new ceiling forward; the workflow itself never performs this increase automatically.
18. **When does review convergence fail?** When any configured budget ceiling (`maxReviewAttempts`, `maxAutomaticFixCycles`, `maxIncompleteReviewRetries`, `maxReviewerQuestionCycles`) is reached without the run having become `converged` (complete Approved review, zero open blockers, exact-target match, full validation passed).
19. **Can a P3 finding trigger another cycle?** Not automatically. It is recorded in the ledger as `accepted-non-blocking`/non-blocking and does not, by itself, start a fix/re-review cycle. If practical, non-blocking cleanup is folded into an already-in-progress fix cycle (triggered by a real blocking finding), never used to justify a new one on its own.
20. **Does an incomplete review consume the review budget?** It consumes one `maxIncompleteReviewRetries` slot, not one `maxReviewAttempts` slot, so a Reviewer execution hiccup (or a Reviewer that legitimately needs one retry to cover full scope) does not eat into the budget meant to bound genuine review/fix iteration. Once `maxIncompleteReviewRetries` itself is exhausted, the run stops as budget-exhausted (incomplete-review variant), same non-approval guarantees as any other exhaustion.
21. **What happens after a malformed structured review?** Classified `completeness = "invalid"`, never `Approved`, handled identically to Spec 048-051's existing malformed-review handling (blocks or retries per existing precedent) — this feature does not change that path, only adds the `invalid` completeness label alongside it for reporting.
22. **Is a separate final review always required?** No — per FR-017, when a `complete` `Approved` review already exists whose recorded target exactly matches the final validated target, no additional review is inserted. A third/final review is required only when a later review attempt is needed anyway (a genuinely new blocking regression, a reopened finding, or the existing target/coverage mismatch already enforced by Spec 055's `isFinalValidationSatisfied`).
23. **How are exact reviewed and validated targets matched?** Reused unchanged from Spec 055: `{ commit, dirty, dirtyHash }` equality via `targetsMatch`/`isFinalValidationSatisfied`. This feature does not introduce a second target-matching mechanism; `reviewConvergence.js`'s `converged` status additionally requires this existing check to pass.
24. **How are performance metrics stored on resume?** Additively on the existing per-attempt records (`reviewRuns[]`, `validationRuns[]`) and as running totals under `state.orchestration.performanceMetrics`; resuming a run reads and extends these rather than recomputing history, so a duplicate resume never double-counts a review/validation attempt that already completed (Test #79/#80).
25. **Is the run-summary schema version bumped?** No. `schemaVersion` stays `1`, mirroring Spec 055 Architecture Decision 6: every new field (`performance`, `reviewConvergence`) is additive and nested; no existing field is renamed, removed, or reinterpreted.
26. **How are old states interpreted?** A state file with no `findingHistory`-derived ledger, no `reviewBudget`, and no `performanceMetrics` resolves to the documented defaults (§15) and `reviewConvergence.status: "not-started"`; it is never misreported as `converged` or `budget-exhausted` from absent data.
27. **Are slow-test metrics production artifacts or developer-only output?** Developer-only. `npx vitest run ... --reporter=verbose` (Vitest's built-in per-test timing, already used for the baseline in this document) is the supported mechanism; no new dependency or production-code instrumentation is added for this. The attempted subprocess-count instrumentation for this document's baseline (`NODE_OPTIONS=--require <counter>.cjs`) did not propagate into Vitest's forked worker processes and was abandoned in favor of the source-level analysis recorded in `spec.md`'s Baseline section — noted here so the number is not mistaken for an instrumented measurement.
28. **Which performance optimizations are explicitly deferred?** Incremental (diff-only) review; provider-specific token counting; distributed test execution; remote CI orchestration; automatic test selection from changed files; automatic (self-)modification of review budgets; remote PR/merge operations; and any change to `collectGitContext`'s internal `git` plumbing call batching (e.g., consolidating `rev-parse`/`status --porcelain=v2` calls) — a legitimate future lever, but one with production-wide blast radius (every consumer of `gitContext`, including Reviewer-facing prompt content) that this feature does not take on.
29. **Was `reviewBudget.maxReviewerQuestionCycles` actually enforced?** Not at first. The independent Codex review of this feature (P2-001, blocking) found that the Questions-outcome path in `orchestrateCommand.js` checked only the legacy `questionCycle >= maxQuestionCycles` ceiling and never consulted the resolved `reviewBudget.maxReviewerQuestionCycles` at all — so an explicit `reviewBudget.maxReviewerQuestionCycles`/`--max-reviewer-question-cycles` override stricter than the legacy value had no effect, contradicting the CLI help text's claim that "exhausting any of the four ceilings stops with stopReason review-convergence-failed." Separately, `resolveReviewBudget`'s fallback for `maxReviewerQuestionCycles` was a hardcoded default rather than actually mirroring the resolved `maxQuestionCycles` the way `maxAutomaticFixCycles` mirrors `maxFixCycles` (the README/CLI help text's "mirrors the existing `state.maxQuestionCycles` ceiling" claim was aspirational, not implemented). Both fixed together: `resolveReviewBudget` now accepts a `maxQuestionCyclesFallback` parameter and mirrors it exactly like `maxFixCyclesFallback`; the Questions-outcome path now runs the same dual-gate pattern already used for fix cycles (legacy check first, so a default-configuration run's message is unchanged, then `isBudgetExhausted`/`buildExhaustionReport` with `stopReason: "review-convergence-failed"` — see "Reviewer question-cycle budget exhausted" in `orchestrateCommand.js`). Two new tests cover it: one confirming the default mirroring, one confirming a stricter override stops safely before the legacy ceiling would have fired.
30. **Did `git diff --stat` reliably drive the changed-file inventory's line counts and paths?** No. The independent Codex review's second round (P1-001, blocking) found that `--stat`'s human-readable output abbreviates long paths with a leading `"..."` and scales the `+`/`-` bar to fit a fixed display width once a diff is large enough -- confirmed empirically against real git: a 499-line change under a long path rendered as `.../for/testing/file.js | 499 +++++++++++++++++++++` (21 `+` characters, an abbreviated path) rather than the true 499/0. Since `classifyHighRisk`'s line-count rule summed the bar's `+`/`-` characters, a large change could be silently misclassified as low-risk, and the abbreviated path meant a Reviewer could not reliably map an inventory entry back to a real file. Fixed by adding `git diff --numstat` alongside each existing `--stat` call in `collectGitContext` (`stagedDiffNumstat`/`unstagedDiffNumstat`/`committedDiffNumstat`) and having `reviewCoverage.js#buildChangedFileInventory` prefer numstat's exact, untruncated per-file counts whenever the supplied gitContext includes those keys (`hasNumstatSupport`); every pre-existing test/fixture that hand-builds a gitContext object with only the `*DiffStat` fields falls back to the original bar-parsing unchanged, so no existing test needed to change. Writing the regression test for this (a real-git test reproducing the exact long-path/large-diff scenario) also surfaced a second, adjacent bug: `createDefaultGitAdapter`'s `run()` applied a blanket `.trim()` to every git command's output, which strips the leading status-code space from the *first* line of `git status --porcelain` whenever that first entry is an unstaged-only change (e.g. `" M path"` becomes `"M path"`) -- `parseStatusCodes`' fixed-column slicing then read one character into the path, silently truncating it by one leading character and producing a phantom duplicate inventory entry. Fixed by trimming only trailing whitespace from git command output, not leading, since `git status --porcelain`'s two-column status prefix is fixed-width and leading whitespace there is semantically significant (this is safe for every other call site: `rev-parse`/`merge-base`/`log --oneline` output never has meaningful leading whitespace, and `diff --stat`'s single cosmetic leading space was already tolerated by its `\s*`-prefixed regex either way).
31. **Does the new `orchestration.stopReason` field ever disagree with the run summary's derived `run.stopReason`?** No, by construction, but a pre-commit self-review caught a real gap where it could have: `runSummary.js#computeStatusAndStopReason` derives `run.stopReason` purely by regex-matching the free-text `orchestration.reason`, and neither budget-exhaustion message (`"Incomplete review retry budget exhausted (...)"`, `"Review convergence budget exhausted (...)"`) matched any existing pattern, so it fell through to `manual-stop` while `orchestration.stopReason` said `review-convergence-failed` — two disagreeing signals in the same summary, violating the "two signals that can never disagree" invariant Spec 055 established for reviewed/validated target matching. Fixed by having `computeStatusAndStopReason` consult `orchestration.stopReason` (via the schema's `normalizeStopReason`) as authoritative whenever it is explicitly present, rather than relying solely on reason-text pattern matching; `review-convergence-failed` was also added to `runSummarySchema.js`'s `STOP_REASONS` enum. Regression assertions were added to Smoke B and Smoke D (`run.summary.run.stopReason` must equal `run.state.orchestration.stopReason`) so this cannot silently regress.
