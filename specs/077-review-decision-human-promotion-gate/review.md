## Blocking Findings

### Round 1 (commit `d3a092c`) — fixed in `d9f04f2`
- **P1-001** — `OfficeProjectPortalView.ts:348-357`: the `[REVIEW DECISION]` dashboard row was built by `createReviewDecisionDisplayRows` from only the latest `ReviewerRuntimeResult` and `ReviewPromotionCollection`, never calling `ReviewDecisionService.classify` or revalidating the plan/readiness/approval/preflight/runtimeStart/implementerRuntime chain. This contradicted `plan.md` and `contracts/review-decision-contract.md`, which require the dashboard render and the Promote precondition to read the identical classification, and could show a confident "Approved; Promote (P)" row on a chain `classify()` would have reported as Stale. **Fixed**: extracted `resolveReviewDecisionInput` in `ReviewDecisionService.ts` as the single shared assembly of `ReviewDecisionInput` from raw per-project stage collections; both `OfficeProjectPortalController.promoteReviewForPromotion` and `OfficeProjectPortalView.render` now call it and pass the result to `ReviewDecisionService.classify`, so the dashboard and the Promote precondition always classify from the same input. `ReviewDecisionView.createReviewDecisionDisplayRows` now takes a `ReviewDecisionClassification` directly instead of re-deriving its own narrower check from a raw `ReviewerRuntimeResultCollection`. Added regression coverage in `ReviewDecisionView.test.ts` for the Stale-classification and promotion-gone-stale cases.

  Deviated from the reviewer's literal `recommendation` (have the Controller compute `classify()` once and thread the result into `render()`): that would require changing `render(state)`'s signature across ~50 existing call sites, or introducing a "controller precomputes into state" pattern with no precedent elsewhere in the codebase. Every other dashboard row is instead computed by the View itself, purely from `state`, at render time (the "latest per project" pattern). Having the View call `classify()` directly follows that same existing pattern and fully satisfies the finding's substance (classify() must back the dashboard, using the same shared assembly as Promote) with a smaller, more consistent diff.

### Rounds 3-4 (commit `24b8c28`, Codex CLI) — fixed in the following commit
- **P1-001** — `ReviewDecisionService.ts:359-360` (`validateChain`): the final chain check verified only `reviewerRuntimeResult.reviewerRuntimeId === reviewerRuntime.reviewerRuntimeId`, never that `reviewerRuntimeResult.status`/`.decision` actually match `reviewerRuntime.status`/`.decision`. Independently reproduced by two separate Codex passes (round 3 and round 4, same HEAD, same root claim), which is why this was fixed rather than triaged as a one-off false positive.

  Reachability trace performed before deciding to fix: through `ReviewerRuntimeService.startReviewer`'s primary construction pipeline, a Runtime and Result sharing a `reviewerRuntimeId` are always written atomically/identically — either via the fresh "spawned" success path or via the existing-runtime idempotency mirror — so no divergence is reachable through that path today. The two controller-level branches that write synthetic Results directly (`OfficeProjectPortalController.startReviewerRuntimeForPromotion`'s "start-stale"/"active-block" branches) never set `reviewerRuntimeId` on those synthetic Results, so they can never match an existing Runtime's id either. No currently-reachable production path was found that produces the exact divergent state Codex describes.

  **Fixed anyway**, because the correct precedent is not round-2's `N-001` (truly unreachable, accepted) but round-1's `P2-001` (fixed): `validateChain`'s own docstring claims to mirror `ReviewerRuntimeService.validateContext` field-by-field, and that sibling function *does* check `implementerRuntime.status !== "Completed" || implementerRuntimeResult.status !== "Completed"` (runtime/result status parity) plus `implementerRuntimeResult.projectId !== plan.projectId` (result-side project linkage) before trusting the Implementer stage — checks `validateChain` was missing for the equivalent Reviewer stage. Two independent reviewers agreeing that a defense-in-depth check present on every other stage's sibling record is absent here, on the feature whose entire purpose is the human promotion gate's integrity, outweighs a reachability trace against today's call sites — a future refactor could introduce a new construction path the trace didn't anticipate.

  **Fix**: extended the final check in `validateChain` to also require `reviewerRuntimeResult.projectId === plan.projectId`, `reviewerRuntimeResult.status === reviewerRuntime.status`, and `reviewerRuntimeResult.decision === reviewerRuntime.decision`, returning the same existing `REVIEW_PROMOTION_REVIEWER_NOT_COMPLETED` reason code (no new reason code introduced). Four existing `classify`/`promote` tests that mutated only `reviewerRuntime`'s status/decision without updating the paired `reviewerRuntimeResult` (a test-fixture convenience, not a realistic scenario) were updated to keep both records in sync, matching the now-enforced invariant. Added two new regression tests (`ReviewDecisionService.test.ts`) proving a diverging Result now collapses classification to `Stale` and blocks Promote with `REVIEW_PROMOTION_REVIEWER_STALE`, rather than being silently trusted.

### Round 7 (commit `2475e6c`, Codex CLI) — fixed below
- **P1-001** — `ReviewDecisionService.ts:33-35, 487-491`: `ReviewerRuntimeService.startReviewer` has three paths (`createBlockedOutcome`'s malformed-command/context/role/target validation failures, a provider `invoke()` throw, and the inline pre-spawn "not spawned" branch for a provider-reported Blocked/Failed outcome) that construct a `ReviewerRuntimeResult` with no matching `ReviewerRuntime` record at all — `reviewerRuntimeId` is left `undefined` on that Result. `classify()` returned `Unavailable` immediately whenever `input.reviewerRuntime` was absent, without ever inspecting `input.reviewerRuntimeResult`, so a genuine attempted-and-Blocked or attempted-and-Failed review was indistinguishable on the dashboard from "review never attempted." Compounding this, `resolveReviewDecisionInput` only looked up a `reviewerRuntimeResult` keyed by `reviewerRuntime.reviewerRuntimeId`, so even a `classify()` fix alone would never have received a populated result in the real dashboard/Promote code paths.

  **Source-of-truth policy** (per the human authorization governing this fix): a `ReviewerRuntimeResult` can truthfully report that a reviewer attempt was Blocked, Failed, or TimedOut — those are real terminal outcomes recorded at the moment they happened. It cannot, alone, prove that an Approved review runtime exists, because promotion's integrity depends on the full `ReviewerRuntime` + `ReviewerRuntimeResult` chain revalidating together (see `validateChain`). So: failure-like result-only states (Blocked, Failed, TimedOut, and Completed/non-Approved) are now surfaced truthfully; any result-only state that would otherwise read as Approved is coerced to `ChangesRequested` instead, since there is no `ReviewerRuntime` to revalidate an Approved decision against.

  **Fix**: `classify()` now delegates to a new `classifyResultOnly(reviewerRuntimeResult)` helper when `input.reviewerRuntime` is absent, instead of returning `Unavailable` unconditionally. A genuine result-only record (`reviewerRuntimeId === undefined`) is classified via a new shared `classifyStatusDecision(status, decision, reviewerRuntimeId)` helper — the same helper the `reviewerRuntime`-present branch of `classify()` now also calls, so the two branches can never diverge on what a given status/decision pair truthfully means. `classifyStatusDecision` maps Blocked/TimedOut/Failed straight through, and Completed to Approved only when `decision === "Approved"` (otherwise ChangesRequested, matching the pre-existing default). `classifyResultOnly` then coerces an Approved result down to `ChangesRequested`, per the source-of-truth policy above. A Result that *does* carry a `reviewerRuntimeId` (a dangling/inconsistent reference to a Runtime that is no longer present, distinct from a genuine result-only record) still returns `Unavailable`, exactly as before — this preserves the pre-existing "no Reviewer Runtime" test's behavior, since that test's fixture always has `reviewerRuntimeId` set. No `reviewerRuntimeId` is ever attached to a result-only classification, so `promote()`'s existing precondition 1 (`classification.reviewerRuntimeId !== request.reviewerRuntimeId`) already blocks promotion for every result-only case without any change to `promote()` itself, `validateChain`, or the controller — no second conditional path was added anywhere, and no `ReviewPromotion` record can be created from a result-only classification.

  `resolveReviewDecisionInput` was extended so a genuine result-only `ReviewerRuntimeResult` can actually be found in production: when no `reviewerRuntime` resolves, it now falls back to matching a Reviewer Runtime Result with no `reviewerRuntimeId` against the current `implementerRuntime.implementerRuntimeId`/`runtimeStart.runtimeStartId` (the only stable identity fields present on a result-only record; `ReviewerRuntimeResult` has no `reviewTargetId`). In production this fallback is always reachable, since `ReviewerRuntimeService.startReviewer` only runs after the Implementer Runtime has Completed, so an `ImplementerRuntime` record always exists by the time a result-only Reviewer Runtime Result can be produced. `OfficeProjectPortalView.render` and `OfficeProjectPortalController.promoteReviewForPromotion` both already called `resolveReviewDecisionInput` then `ReviewDecisionService.classify`/`.promote` on that shared assembly (per the round-1 P1-001 fix), so no change was needed in either call site — both now surface the truthful result-only state identically, satisfying the shared-classification-path requirement without a second conditional path in the controller. `ReviewDecisionView.createReviewDecisionDisplayRows` already had a complete `switch` over every `ReviewDecisionState`, including `TimedOut`/`Blocked`/`Failed`, so the dashboard formatter needed no change either.

  Added regression tests: in `ReviewDecisionService.test.ts`, a table-driven `classify()` suite covering result-only Blocked/Failed/TimedOut, Completed+Unknown, Completed+ChangesRequested, and Completed+Approved (asserting the exact truthful state, never Approved); a test proving a dangling `reviewerRuntimeId` reference still classifies `Unavailable`; a test proving no-runtime-and-no-result still classifies `Unavailable`; table-driven `promote()` tests proving each result-only failure-like status is blocked with no `ReviewPromotion`/`promotionCollection` created; a dedicated test proving a result-only Approved outcome is also blocked with no promotion created; and a source-immutability test. In `OfficeProjectPortalController.review-decision.test.ts`, an integration test drives a real Completed Implementer Runtime then a stubbed pre-spawn Blocked/Failed Reviewer Runtime outcome (the real `ReviewerRuntimeService` result-only shape, no `ReviewerRuntime` record constructed), and asserts that the same `resolveReviewDecisionInput`/`classify()` call the dashboard uses reports the truthful state (`Blocked`/`Failed`) and that pressing Promote is blocked with no `ReviewPromotion` created — proving the dashboard and Promote precondition agree on a live controller-driven chain, not just in isolated unit fixtures.

### Round 8 (commit `e5b9ca0`, Codex CLI) — fixed below

**Scope authorization**: a bounded stabilization pass, explicitly not an open-ended patch/review loop — limited to `P2-001`, `P2-002`, and one narrow adjacent audit of `classify()`'s status-to-decision mapping, `reasonForNonApproved`, `promote()` precondition ordering, actor validation, existing-promotion idempotency, `granted` semantics, result-only state handling, and the shared dashboard/Promote classification path. Explicitly not a broad validation-parity audit and not a refactor of unrelated Reviewer Runtime/Execution Chain services.

- **P2-001** — `ReviewDecisionService.ts` (`reasonForNonApproved`): the status-to-reason-code mapping was lossy. Every non-Approved classification other than a genuine `ChangesRequested` decision or the (unreachable via `promote()`) `Unavailable`/`Stale` cases fell through to the single generic `REVIEW_PROMOTION_REVIEWER_NOT_COMPLETED`, so a human looking at a blocked-promote reason code could not distinguish a reviewer that was Blocked, one that TimedOut, one that Failed, one that Completed with a genuine `ChangesRequested` decision, and one that Completed but the provider's decision itself came back `"Unknown"` — five materially different terminal outcomes collapsed into one code.

  **Reason-code policy** (governs this fix): each `ReviewerRuntimeStatus` value that reaches `reasonForNonApproved` gets its own truthful reason code, reusing an existing code only where one already truthfully describes that exact outcome, and adding the smallest coherent new set otherwise — no new `ReviewDecisionState` enum value was introduced (that would have rippled into `ReviewDecisionView.ts`'s switch and every other state consumer, beyond this pass's bounded scope). No failure-like or unknown-decision outcome may ever map to `Approved`, and none of these states may ever back a `ReviewPromotion`.

  **Fix**: added `REVIEW_PROMOTION_REVIEWER_BLOCKED`, `REVIEW_PROMOTION_REVIEWER_TIMED_OUT`, `REVIEW_PROMOTION_REVIEWER_FAILED`, and `REVIEW_PROMOTION_REVIEWER_DECISION_UNKNOWN` to `ReviewPromotionReasonCode` (`ReviewDecisionTypes.ts`). `reasonForNonApproved` now takes the full `ReviewDecisionClassification` (previously just the bare `state`) and switches on `.state`, returning the new Blocked/TimedOut/Failed codes directly, and — for `ChangesRequested` — returning `REVIEW_PROMOTION_REVIEWER_DECISION_UNKNOWN` when the classification's new optional `decision` field is `"Unknown"`, or the existing `REVIEW_PROMOTION_DECISION_NOT_APPROVED` for a genuine `ChangesRequested` decision (that code is now reserved exclusively for the genuine case). `REVIEW_PROMOTION_REVIEWER_NOT_COMPLETED` is left in the reason-code union and as `reasonForNonApproved`'s `default` case, since it remains genuinely load-bearing elsewhere in `validateChain`'s chain-parity mismatch checks — those uses are unrelated, pre-existing, and out of this pass's scope.

  To surface the Unknown-vs-ChangesRequested distinction without a new `ReviewDecisionState` value, `ReviewDecisionClassification` gained an optional `decision?: ReviewerRuntimeDecision` field, threaded through only where truthfully known: `classifyStatusDecision`'s `Completed`-with-non-Approved branch and its `default` (result-only) branch now attach the raw `decision`. `classifyResultOnly`'s pre-existing Approved-result-coerced-to-`ChangesRequested` branch (see Round 7) deliberately does *not* attach `decision: "Approved"` — that branch's own rationale (no `ReviewerRuntime` exists to revalidate an Approved decision against) means it must fall through to `REVIEW_PROMOTION_DECISION_NOT_APPROVED`, not the new Unknown-specific code, and no code change to that branch was needed since it simply never sets the new field. `ReviewDecisionView.ts` was inspected and needed no change: its `switch` reads `classification.state` only, already has distinct display text for every `ReviewDecisionState` value, and never calls `reasonForNonApproved`.

  Architectural fact confirmed during test-writing (not a defect introduced by this pass, and not fixed): `promote()`'s precondition 1 (target-mismatch) always intercepts before precondition 2 (`reasonForNonApproved`) whenever the classification carries no `reviewerRuntimeId` — true for every result-only classification and for `Unavailable`. This is the same pre-existing behavior Round 2's own `N-001` non-blocking finding already documented for `REVIEW_PROMOTION_REVIEWER_MISSING`; it means the four new status-specific codes are reachable via `promote()` only when a full `ReviewerRuntime` record with a matching `reviewerRuntimeId` is present (not for result-only outcomes, which correctly and truthfully report `REVIEW_PROMOTION_TARGET_MISMATCH` instead, since the request names a `reviewerRuntimeId` the classification cannot confirm).

  Added regression tests in `ReviewDecisionService.test.ts`: a table-driven `promote()` suite against a full (non-result-only) Reviewer Runtime chain, one case per status (`Blocked`, `TimedOut`, `Failed`, `Completed`+`ChangesRequested`, `Completed`+`Unknown`), asserting the exact new reason code and that `REVIEW_PROMOTION_REVIEWER_NOT_COMPLETED` never appears; a `classify()`-level test confirming a never-attempted (no runtime, no result) chain still classifies `Unavailable` and blocks `promote()`, without asserting a specific promote()-level reason code (since `REVIEW_PROMOTION_REVIEWER_MISSING` remains promote()-unreachable, per N-001); the existing result-only Blocked/TimedOut/Failed `promote()` test was left asserting only `granted: false`/no promotion, since target-mismatch — not the new codes — is what actually fires there.

- **P2-002** — `ReviewDecisionService.ts` (`promote`): the existing-`ReviewPromotion` idempotency short-circuit was checked before the requesting actor was validated. A first-time request with an invalid actor was correctly rejected, but once a valid promotion existed for a `reviewerRuntimeId`, a *repeat* request carrying an invalid, automation-style, or bot/agent actor label (`"Codex"`, `"Claude"`, `"agent-runner"`, `"release-bot"`, `"automation-script"`, empty string, etc.) could reach the idempotency path and receive `granted: true` alongside the existing promotion record, without ever having its own actor checked.

  **Actor-before-idempotency policy** (governs this fix): actor validation must run before the existing-promotion idempotency short-circuit, for both first-time and repeat requests, so an invalid actor can never receive `granted: true` merely because a valid promotion already exists for that `reviewerRuntimeId`.

  **Fix**: reordered `promote()`'s preconditions so `getActorBlockReason(request.actor)` (→ `REVIEW_PROMOTION_INVALID_ACTOR`) runs immediately after the `reasonForNonApproved` check and before the existing-promotion lookup, which now runs last. A valid actor repeating a request against an existing promotion still returns the same record idempotently (`REVIEW_PROMOTION_ALREADY_PROMOTED`, `alreadyPromoted: true`, `granted: true`) exactly as before; an invalid actor repeating the same request now receives `granted: false` and `REVIEW_PROMOTION_INVALID_ACTOR`, with the existing `ReviewPromotion` record left completely unmutated (no deletion, no overwrite, no new record).

  Added regression tests in `ReviewDecisionService.test.ts`: valid-actor first-time promotion; valid-actor idempotent repeat; first-time invalid actor blocked before any idempotency check exists; a table-driven `it.each` (`"Codex"`, `"Claude"`, `"agent-runner"`, `"release-bot"`, `"automation-script"`, `""`) asserting every listed invalid-actor label, on a *repeat* request against an already-promoted `reviewerRuntimeId`, receives `granted: false` with `REVIEW_PROMOTION_INVALID_ACTOR` and not `REVIEW_PROMOTION_ALREADY_PROMOTED`; and a no-duplicate-promotion test snapshotting the promotion collection before and after an invalid repeat request to confirm it is byte-for-byte unmutated. Added an integration-level regression test in `OfficeProjectPortalController.review-decision.test.ts` (table-driven over the same invalid-actor labels) that drives a full chain to Approved via the controller/view's own shared `resolveReviewDecisionInput`, then calls `ReviewDecisionService.promote` directly with an invalid actor (the controller itself hardcodes `actor: "Local Human"` with no external input, confirmed by reading `OfficeProjectPortalController.promoteReviewForPromotion`, so invalid-actor behavior can only be exercised at the service level in this integration context) — asserting the block, and separately asserting `classify()` still reports `Approved` and the dashboard's `createReviewDecisionDisplayRows` still shows "Promote (P)" rather than any "Promoted by" success text, proving the dashboard never shows success for an actor-invalid request.

## Comprehensive parity audit (Round 6 authorization)

Following round 5's third distinct parity-gap finding, one comprehensive field-by-field audit of `ReviewDecisionService.validateChain` against `ReviewerRuntimeService.validateContext`/`validateRoleBinding`/`validateReviewTarget` was authorized and performed, rather than fixing round 5's specific finding in isolation. Method and full field-by-field matrix (matches / intentionally differs / not applicable / missing) recorded in `.agent-workflow/spec-077-parity-audit.md` (gitignored working artifact, not part of the shipped product). Audit scope rule: mirror what the sibling validators actually check, not the full type surface of each record — e.g. `RuntimeStart.executionReadinessResultId` exists on the type but `validateContext` itself never checks it, so it was out of scope to add here too.

**Fields added to `validateChain`** (all reusing existing reason codes — no new reason code introduced):
- Runtime Start block (`REVIEW_PROMOTION_START_STALE`): `executionPlanId`, `humanExecutionApprovalId`, `runtimePreflightId`, `taskId`, `confirmedAssignmentId`, `preparedSessionId`, `activeSessionId`, `employeeId`, `worktreePath`, `repositoryRoot` (vs `plan.repositoryPath`), `branch`, `specificationPath`.
- Implementer Runtime block (`REVIEW_PROMOTION_IMPLEMENTER_NOT_COMPLETED`): `worktreePath`, `branch`, `specificationPath`, and a `reviewerStarted`/`validationStarted`/`githubMutationStarted`-all-false guard (verified: these fields are typed as literal `false` and never constructed as `true` anywhere in the codebase, so this addition is zero-risk parity, not a behavior change).
- Review Target block (`REVIEW_PROMOTION_TARGET_MISMATCH`): `worktreePath`, `featureBranch` (note: `ReviewTarget` uses `featureBranch`, not `branch`, unlike the other three record types in this chain), `specificationPath`, and `workingTreeState === "Clean"`.
